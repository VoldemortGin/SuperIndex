### ⚠️ 关键踩坑（务必记住）
**PageIndex flash 的 PDF 解析用 `ProcessPoolExecutor(mp_context=spawn)`**
（`pageindex/flash/parser_pdfium_parallel.py`）。因此：
- 调用脚本**必须是真实文件**且带 `if __name__ == "__main__":` 保护；
- **绝对不要用 heredoc / stdin 方式跑**（`python - <<'PY'`）——spawn 的子进程
  无法重新导入 stdin 的 `__main__`，表现为**进程挂死、无任何网络请求**（我卡了 5 分钟才发现）。
- 判断依据：`lsof -nP -iTCP | grep ESTABLISHED` 里看不到该进程的连接，即说明卡在 spawn 而非在调 LLM。

   `import pageindex.utils as u; u.SUMMARY_CONCURRENCY = n` 猴补丁生效
   （`utils.py:851` 在调用时读该模块全局量，所以运行时改有效）。
2. **韧性**：`index_documents()` 改为**逐份文档重试 3 次 + 指数退避（30s/60s）**，
   失败则跳过该文档继续跑，最后汇总失败清单——不再让单份文档或单次瞬时错误
   拖垮整轮。
3. 日志改 `flush=True` / `python -u`，便于实时观察。

## 追加：Web 聊天查询界面（用户要求）

用户要求「给 AIA report 构建一个 web 聊天查询界面，方便动态提问」。

### 实现（零额外依赖）
- `webapp/server.py` —— 纯 Python 标准库 `http.server` + `ThreadingHTTPServer`，
  **没有引入 FastAPI/uvicorn**（venv 里也没装）。端口 **8787**（8000 被用户
  另一个 GraphRAG 项目占用）。
- `webapp/static/index.html` —— 单文件前端，原生 JS，浅色主题。
- 路由：`GET /`、`GET /api/status`、`POST /api/ask`（SSE 流式）、`GET /api/health`。
- SSE 事件名：`answer`/`thinking`/`tool_call`/`tool_result`/`error`/`done`。
  用 `client.chat(q, doc_id=..., stream=True)` 再迭代 **`.events`**（不是直接迭代
  ChatStream，那样只有纯文本，拿不到工具调用）。

### 设计要点 / 踩坑
- **必须迭代 `.events` 而非文本流**：只有 events 才带 `tool_call`/`tool_result`，
  这正是 PageIndex「可追溯」的卖点。实测一次问答会看到
  `get_document_structure` → `get_page_content(pages="14-16")` 两步。
- **thinking 是逐 token 流式下发的**（实测 179 个 thinking 事件 / 146 个 answer 事件），
  如果每个事件都新建一个 step，面板会被刷成上百条。前端改成把连续 thinking
  delta **折叠进同一个 step**，遇到 tool_call/tool_result/answer 才断开。
- `ThreadingHTTPServer` + 全局 `_chat_lock`：聊天串行化，避免两个标签页
  在同一个 PageIndex client 上交错跑 run。
- SSE 走 HTTP/1.0 无 Content-Length，靠连接关闭结束，每块都 `flush()`。
- 前端每 20s 轮询 `/api/status`，索引中的文档显示「索引中」并禁用，
  跑完自动可勾选——这样索引还在跑的时候界面就能用。

## 追加：向用户讲解 PageIndex 原理（备查的代码事实）

用户要求解释 PageIndex 的查询流程与原理，用可视化图讲了一遍。查证到的关键事实：

- **本地模式只暴露 5 个工具**（`pageindex/agent_tools.py` 的 `TOOL_CONTRACT`）：
  `browse_documents`、`get_document`、`get_document_structure`、`get_page_content`、
  `remove_document`。云模式另有 `search_documents` / `get_folder_structure` 等。
- 树的每个节点只存 **标题 + start_index/end_index + summary**，不存正文
  （`config.yaml` 的 `if_add_node_text: "no"`）。所以整棵树很小，可以整体喂给模型 ——
  这是「让模型看目录做决策」而非「算相似度」的前提。
- 实测 FY2021：304 页 → 488 节点、树深 6；一级节点为
  Cover / About AIA / Our Purpose / Contents / 2021 Highlights /
  Transforming through Technology… / AIA At-A-Glance /
  Overview p12-23 / Financial and Operating Review p23-74 /
  Corporate Governance p74-134 / Financial Statements p134-289 /
  Additional Information p289-303 / Inside Back Cover / Back Cover。
  股息 146.00 港仙的命中路径：Overview → Chairman's Statement (p14-17) → p15。
- 真实检索轨迹（问 FY2021 每股股息）：
  `get_document_structure` → `get_page_content(pages="14-16")` → 作答。
  一次问答通常只有 2 次工具调用，只读极少数页面。
- 成本结构：索引约 $0.001/页（一次性）；查询只读推理到达的节点，
  所以查询成本**不随文档长度增长**（官方口径：原生 PDF 直塞在 52 页贵 2.1×，
  420 页贵 16.6×，805 页直接超上下文）。
- 局限：本地模式只支持**有文本层的 PDF**，无 OCR、无图像理解、无 folder。

## 追加：tree.json 与 pages.json 的分工（备查）

用户问「doc Pages 和 Tree 分别怎么用的」。查证结果：

- **写入**（`local_api.py:140-159`）：
  `pages = [{"page_index": i+1, "markdown": text} for i, text in enumerate(page_texts)]`
  然后 `save_document(doc_id, meta, remove_fields(structure, fields=["text"]), pages)`
  —— 注意树在存盘前**显式剥掉 `text` 字段**。落到
  `results/pageindex_store/docs/<doc_id>/{tree.json, pages.json, doc.json}`。
- **读取映射**（关键，别搞混）：
  - `get_document_structure` → `raw_tree(doc_id)` → `store.get_tree()` → **读 tree.json**
    （源码注释：`_format_structure strips text anyway — don't download it.`）
  - `get_page_content` → `client.get_ocr(doc_id, format="page")` → `store.get_pages()`
    → **读 pages.json**，再按请求的页码过滤
- **体积实测**（FY2021）：PDF 3.5MB / pages.json 0.80MB / tree.json 430KB（摘要占 380KB）。
  树约为正文的 52%。
- **响应体上限**：`TOOL_RESPONSE_CHAR_LIMIT = 100_000`，
  `_CHAR_BUDGET = 95_000` 字符。结构超限会切成 `parts` 分页返回（`part=N`）；
  页正文超限会截断并提示「Pages X were omitted due to response size limits」。
- 设计要点：树是**故意有损**的导航地图（只答「在哪」，不答「是什么」），
  正文按需取。这个拆分让查询成本与文档长度解耦。

## 追加：上千份文档时的扩展问题（用户提问）与官方解法

用户问：「当我有上千份文档时，文档 list 很庞大，如何解决？」

### 现状核实（代码事实）
- **OSS 本地模式是扁平的**：`local_api.py` 多处显式拒绝 ——
  `folders are not supported in local mode`（:81、:355）、
  `Folders are not supported in local mode yet`（agent_tools.py:508）、
  `Relevance ranking is not supported in local mode yet`（agent_tools.py:742）。
- `browse_documents` 参数：`limit`（1–50，默认 10）、`offset` / `next_offset`、
  `sort`（time | relevance，本地只支持 time）、`query`（relevance 必需）。
  → 上千份文档在本地只能靠**翻页**，且无语义排序，实际不可用。
- **OSS 云模式**（`PageIndexCloudClient` + api key）：支持 folder 树、
  relevance 排序、`search_documents`。客户端方法：
  `create_folder` / `list_folders` / `get_folder_path` / `get_folder_id` /
  `get_document_path` / `folder_context`。
- `search_documents` 在 TOOL_CONTRACT 里**没有**（本地注册表只有 5 个工具），
  是云能力的升级路径。

### 官方解法：PageIndex File System（Enterprise，Cloud 随后）
来源：`pageindex.ai/blog/pageindex-filesystem`（2026-05-03）。

核心洞察：**文件系统本身已经是一棵树**。目录套子目录、子目录套文件 ——
这是现成的层级，免费拿到的。所以让文件系统**本身成为节点级的一层**：
每份文档的树挂在文件系统树的叶子上，**整个语料变成一棵大树**。
同一套 tree search 策略既导航目录层级、又下钻到文档内部树，**工具不变**。

但「光有文件夹」在百万级不够用，三个原因：
1. 很多语料**根本没有目录结构**（S3 桶 / SharePoint 就是一坨扁平文件）
2. 层级是**一维的**：一份合同同时属于某供应商、某地区、某财年，
   目录树逼你只选一个轴，用户真正查询的其他轴就丢了
3. **文件夹名对 LLM 是噪声**：`misc/`、`final_v3_USE_THIS_ONE/`、`2019_legacy/`，
   甚至 `/finance/2024/` 也不说明里面讲的是「定价风险」还是「流动性」

三个技术件：
- **虚拟节点**：没有现成层级时**合成**一个 —— 按主题聚类，加上 LLM 推断的
  元数据（类别、摘要、关键实体）作为内部节点。关键是**同一份文档可以挂在
  多个虚拟父节点下**（vendor 且 region 且 year），扁平文件系统表达不了。
- **树是查询相关的**：「vendor X 在 2024 年收了多少」要 vendor→year 的树；
  「下季度到期的合同」要 status→renewal date 的树。同一语料，两棵完全不同的树。
  按查询**按需构建**，不需重新入库或重新 embedding。
- **遍历策略自适应**：子节点标签有信息量时用 **layer-wise**（逐层下钻、按标签剪枝）；
  标签无信息量时用 **recursive / 动态扁平化**（把子树压到叶子，把区分工作
  推迟到内容层）。这保证搜索深度只与「真正携带信息的深度」成正比。

### 给用户的建议路径（三档）
1. **今天就能做（OSS 本地）**：自己加一层路由 —— 先粗筛出候选文档子集，
   再对这些跑 PageIndex。等于手搓一个「穷人版文件系统」。
2. **OSS 云版**：folder 树 + relevance 排序 + `search_documents`，可用但需自己维护层级。
3. **Enterprise / Cloud File System**：虚拟节点 + 查询相关树 + 自适应遍历，官方方案。

## 追加：查询延迟诊断（用户反馈「响应不够快」）

写了 `scripts/profile_query.py` 做实测。方法：monkeypatch `litellm.acompletion`
抓每次调用的 prompt/cached/completion tokens 与耗时（**litellm 的
`success_callback` 在 openai-agents 路径下不触发，必须直接包 `acompletion`**）。

### 实测数据（3 份已索引文档，deepseek-flash）
| 场景 | LLM 调用 | 墙钟 | 累计 prompt | 峰值 prompt |
|---|---|---|---|---|
| 单文档 · 浅层问题（答案在前部） | 3 | 3.6s | 19,714 | 9,890 |
| 单文档 · 深层问题（答案在财报附注） | 4–5 | 4.6–10.3s | 74,694 | 48,234 |
| 多文档（3 份） | 3 | 5.7s | 37,352 | 21,033 |
| Web UI 端到端（SSE） | 3 | 3.9s | — | — |

### 根因（按影响排序）
1. **树太大且被切成 9 片** —— 这是根本原因。
   `_CHAR_BUDGET = 95,000`；FY2021 整棵树 **452,593 字符 ≈ 113K tokens**，
   `get_document_structure` 的 `total_parts = 9`，单片最大 94,973 字符。
   摘要平均 **1,167 字符**（333 节点 × 1,167 ≈ 388K 字符）—— 摘要过长是元凶。
   后果：深层问题要多拉几片，每拉一片整段对话重发一次。
2. **每回合重发全部前缀**：prompt 实测增长 1,965 → 7,823 → 43,547 → 46,356 → 48,234。
   累计 prompt 是最终 prompt 的 3–4 倍。DeepSeek 缓存有效（后段命中 83–95%），
   但**大块内容首次进 prompt 必须冷处理**，那一下就是几秒。
3. **推理 token**：Web 端一次问答有 167–230 个 thinking 事件。
4. **agent 循环最少 3 次往返**（决策→读结构→读正文→作答），架构决定的固定成本。
5. 本地 I/O **不是**瓶颈：tree.json read+parse 0.8ms、pages.json 1.8ms、
   `get_page_content(3 页)` 仅 3ms。已排除。
   （但注意 `get_page_content` 内部走 `get_ocr(format="page")`，
   会把整份 pages.json 解析成 304 条再按页过滤 —— 本地无所谓，云上要改。）

### 已实施的优化（已验证）
**`reasoning_effort="low"`** —— 同一个深层问题：
- 默认：5 次调用、**10.29s**、输出 1,646 tokens、峰值 prompt 48,234
- low：5 次调用、**5.80s**、输出 629 tokens、峰值 prompt 20,498
- 即 **−44% 墙钟、−62% 输出 token，答案不变**（US$60,467m，已核对 p37）

已写进 `webapp/server.py`，通过环境变量控制：
`REASONING_EFFORT = os.getenv("PAGEINDEX_REASONING_EFFORT", "low").strip() or None`，
调用处 `client.chat(..., reasoning_effort=REASONING_EFFORT)`。
`.env.example` 已补文档。注意：`low` 只是**减少**思考，并非关闭（仍有 230 个 thinking 事件）。

### 尚未实施（按性价比）
- **缩短节点摘要**（根治，需重新索引）：avg 1,167 → 300 字符，
  树从 113K → ~35K tokens，很可能不再分页（9 片 → 1–2 片）。
- 调 `_CHAR_BUDGET` 减少分片往返（权衡：单片变大）。
- 多文档问题先做文档级路由，别并行塞多棵树。
- Web UI 全局 `_chat_lock` 换成按 doc 的细粒度锁。
- 高频问题答案缓存。

## 追加：多文档检索的扩展性（用户提问）

用户反馈「问题可能横跨集合里多个文档时，搜索时间明显增长」。实测曲线
（问题固定为「列出每份报告的每股股息」，`reasoning_effort=low`）：

| docs | calls | wall | cum_prompt | peak_prompt | cold_tok |
|---|---|---|---|---|---|
| 1 | 8 | 21.52s | 421,814 | 102,899 | 98,870 |
| 2 | 3 | 5.71s | 37,493 | 21,529 | 19,573 |
| 3 | 3 | 6.28s | 76,113 | 40,362 | 38,225 |

三个关键结论：
1. **每加一份文档 ≈ +19K 冷 token**（peak 21,529 → 40,362）。线性累积，
   外推 10 份 ≈ 174K、20 份 ≈ 365K peak prompt，直接撞上下文上限。
2. **多文档场景下缓存基本失效**：`cold ≈ peak`（19,573/21,529、38,225/40,362）。
   因为每份文档的结构都是全新内容，必须冷 prefill。这是单文档场景没有的问题
   （单文档靠前缀缓存能命中 83–95%）。
3. **范围给错比给大更糟**：1 文档那次跑了 8 次调用 21.5s —— 问题问「每份报告」
   但 scope 只有一份，模型反复找不到、陷入长循环。

### 根因
不是「搜索慢」，而是**所有候选文档的结构共用一个上下文**。上下文长度直接决定
prefill 时间，所以成本是 O(N)，且没有缓存可以吸收。

### 优化方案（按性价比）
1. **两段式：先路由再深挖**（架构性，收益最大）
   - 阶段1：全集合文档级摘要表（1000 份 × 100 字符 ≈ 25K tokens，一次调用）
   - 阶段2：只对选中的 1–2 份跑完整 PageIndex
   - 上下文里永远只有 1–2 份文档，与集合大小解耦
   - 即 PageIndex File System 的核心思路
2. **并行 fan-out + 归并**：候选文档并发跑独立 PageIndex run（各自独立上下文），
   串行 N× → ~1× 墙钟。实现：线程池 + 每线程一个 client。
3. **路由阶段只给目录不给摘要**：outline（标题+页码，6.8K tokens/份）
   vs 完整结构（109K tokens/份），3 份 triage 从 300K+ 降到 20K。
4. 缩短摘要（对多文档收益翻倍）
5. **预抽取跨文档事实表**：索引时把股息/VONB/OPAT 等数值抽成小表，
   跨文档数值题直接从表答，不用读 N 棵树。金融报告特别适用。
6. Web UI 全局 `_chat_lock` → 允许并发（否则长查询堵住整个界面）

### 备查：树的体积构成（FY2021，紧凑 JSON）
- 完整（标题+页码+摘要+key_items）：435,687 字符 ≈ **108,921 tokens**
- 去掉摘要：42,421 字符 ≈ **10,605 tokens**（1 片）
- 极简（标题+页码）：27,275 字符 ≈ 6,818 tokens
- **摘要文字占 89%**（388,929 字符）—— 摘要过长是树膨胀的元凶

## 追加：命中页面后取到的正文到底是什么格式（用户提问）

**结论：不是 PDF 原文，也不是 OCR —— 是 PDF 自带的文本层（text layer）。**

- 提取实现：`local_api.py:195 _extract_page_texts()` 用 **PyPDF2** 的
  `page.extract_text()` 逐页抽文本，再 `_scrub_surrogates()` 清掉孤立代理字符。
- **本地模式完全没有 OCR**：全仓库 grep `ocr` 在 .py 里零命中（除了工具名 `get_ocr`）。
  README 也明写 OSS = "no OCR"；云版才有 OCR & image understanding。
- 存储：`pages.json = [{"page_index": int, "markdown": str}]`，一页一条。

### ⚠️ 字段名叫 `markdown`，但内容不是 markdown
实测 FY2021 全 304 页的 `markdown` 字段：ATX 标题 `#` **0** 个、表格竖线 `|` **0** 个、
粗体 `**` **0** 个、反引号 **0** 个。就是**带换行的纯文本**。别指望能解析成结构化 markdown。

### 保真度按内容类型差异极大（重要）
- **正文**：几乎完美（这也是 PageIndex 官方 benchmark 只测 running-text 事实的原因）
- **简单表格**：尚可。p37 的资产负债表抽成
  `Financial investments 281,876 271,467 4%` —— 行标签 + 数值，能读
- **图表 / 复杂表头**：**严重退化**。p12（Results at-a-glance）抽出来是
  `2018 2019 2020 2017US$ MILLIONS` 后接 `4,154 / 3,366 / 2,7653,955 / 3,206`，
  年份乱序、数值与年份脱钩；柱状图那组更糟：`175230`、`190284`、`229326`
  两个数直接粘成一个数。**标签↔数值的关联被破坏**，数值查询基本不可用。

### 顺带发现的工具差异
- PageIndex 存 `pages.json` 用 **PyPDF2**
- 我的 ground-truth 脚本 `scripts/extract_text.py` 用 **pypdfium2**
- 两者抽同一份 PDF 的文本层，结果会有细微差异。核对答案时要知道这点。

### 实践建议
财务数值题尽量避开图表页；AIA 那类「Results at-a-glance」页面的数字
应以正文（主席报告/CFO 回顾）或 xlsx 财务补充资料为准。

方法：patch `litellm.acompletion`，把 `kwargs['messages']` 存下来，跑一次真实问答。
（openai-agents 路径下这是唯一可靠的抓包方式。）

### 页面正文的承载形状（三层嵌套）
```json
{
  "role": "tool",
  "tool_call_id": "call_00_MdMzHXIJ128afhYmeuqC2953",
  "content": [
    { "type": "text",
      "text": "{\"success\": true, \"doc_name\": \"...\", \"total_pages\": 304,
```

## 追加：Markdown 输入路径 vs PDF 路径（用户提问）

用户问「已有处理好的 markdown，相对 PDF 页面有什么差距」。查证结果：

### 两条路径确实都存在
- PDF：`page_index_flash()` → 书签 + 排版统计建树
- Markdown：`md_to_tree()`（`pageindex/page_index_md.py`）+ CLI `run_pageindex.py --md_path`

### ⚠️ 但本地 client 只吃 PDF
`local_api.py:105-107` 明确拒绝：`"only PDF files are supported in local mode"`。
`client.py` / `agent_tools.py` 里没有任何 markdown **输入**支持
（搜到的 "markdown" 都是输出字段名和引用渲染）。要喂 md 只能走 CLI 或直接调 `md_to_tree()`。

### 核心差距：寻址单位不同
| | PDF 路径 | Markdown 路径 |
|---|---|---|
| 节点字段 | `start_index` / `end_index` | **`line_num`** |
| 单位 | 页码**区间** | 单个**行号** |
| 引用形式 | 「p14–17」 | 「第 1234 行」 |
| 树来源 | 书签 + 排版统计（语义推断） | 正则 `^#{1,6}\s+` / `^\*\*...\*\*$`（纯语法） |

### ⚠️ markdown 路径是「只有树、没有内容库」
`md_to_tree()` 只返回 `{doc_name, line_count, structure}`，**没有 pages 对应物**。
而 `get_page_content` 依赖 pages.json（只有 PDF 路径会建）。
默认 `if_add_node_text='no'` 会在生成摘要后把 text 剥掉 →
**树里只剩标题+摘要，没有任何办法取回正文**。
要用 agent 工具检索，必须自己建内容库。

### 收益 / 损失
收益（前提是转换器够好）：表格变 markdown 表格 → 图表/表格退化问题基本解决（最大收益）；
标题显式、树更干净；阅读顺序被修正；无页眉页脚噪声；公式可保留。
损失：**页码消失**（PageIndex 整个寻址体系建立在页码上；页码是财务报告审计核对的基本单位）；
无法从答案跳回原 PDF 页；转换质量成为新的单点故障且不可追溯；
正则解析对格式敏感（没有规范 `#` 标题则树退化）。

### 建议
保留页码锚点：转换时插入 `<!-- page: N -->` 标记，自定义 md→tree 适配层把
`line_num` 映射回页码，让节点同时带 `page` 字段 —— 兼顾 markdown 的表格质量与页码引用。

## 追加：原生 Markdown 语料的实测（用户澄清是公司自有 md，非 PDF 转换）

写了 `scripts/03_md_tree_probe.py` 实测（样本 `samples/aia_ar2021_excerpt.md`）。

### 实测结果：建树质量很好
49 行 → **9 节点、深度 3**，层级与 `#`/`##`/`###` 完全对应。
节点字段：`['line_num','node_id','nodes','prefix_summary','summary','title']`。
表格**原样保留**在节点 `text` 里（完整 markdown 表格），因为
`get_node_summary()` 里：**节点文本 < summary_token_threshold 时直接返回原文当摘要**，
不调 LLM。所以短章节的表格直接进了树。

### ⚠️ 踩到三个坑
1. **`md_to_tree()` 有真 bug**：`summary_token_threshold` 默认 `None`，
   而 `get_node_summary()` 做 `num_tokens < summary_token_threshold` → `TypeError`。
   必须显式传值（CLI 默认 200）。说明 md 路径比 PDF 路径测试得少。
2. **默认 `if_add_node_text='no'`** 会在摘要后剥掉 text → 树里没正文可取。
   要检索必须显式 `if_add_node_text='yes'`。
3. **叶子节点写 `summary`，父节点写 `prefix_summary`**（md 路径特有，与 PDF 路径不同）。

### 寻址：line_num 是单点，范围靠推
实测节点范围由「下一个标题的行号」推出，且有 off-by-one：
`[0000] 行 1–3` 与 `[0001] 行 3–9` 都含第 3 行。

### 重要判断
**原生 markdown 的结构是显式且可靠的，PageIndex 的核心价值（从 PDF 排版里「推断」结构）
在这里基本失效。** 对自家规范 markdown，可以用更简单的管线：
按 `#` 切章节 → 章节摘要 → 模型选章节，不必上排版推断 + 树优化那套。
PageIndex 仍有价值的部分：agentic 导航循环、工具契约、引用格式、多文档路由。

### 接入建议（本地 client 不收 md，必须自己搭）
用 `md_to_tree(if_add_node_text='yes')` 建树 + 自建按 `node_id` 索引的内容库，
提供 `get_document_structure`（给树）和 `get_node_content(node_id)`（给内容）两个工具，
引用形式「§0014 Chairman's Statement」—— 对原生 md 比页码更有意义（本来就没有页）。

## 追加：Markdown 格式不规范时的应对（用户实际痛点）

用户澄清：公司 md 格式遵守得不好，含标题/页面/附加信息，**有些是 PPT 转的**。

### 实测两类失败模式（用 `samples/` 里的坏样本验证）
| 样本 | 特征 | 实测结果 |
|---|---|---|
| `bad_no_headings.md` | 全篇无标题 | **预测节点 0、深度 0** → 树完全为空 |
| `bad_ppt_derived.md` | 全篇用 `**加粗**` 当标题 | **节点 6、深度 1** → 扁平，无法层级剪枝 |

关键：PageIndex 的 md 路径**完全靠标题正则**（`^#{1,6}\s+` 和 `^\*\*...\*\*$`），
且**加粗一律当 level 1**。所以这两类文档会**静默失败** —— 不报错，只是索引质量极差。

### 新增工具 `scripts/04_md_audit.py`
不跑 LLM 就能**预测**索引结果（复刻 PageIndex 的正则 + 栈算法）：
- 每份文件：预测节点数/树深、`#` 与 `**` 各自数量、页标/slide 标记、表格、游离文本、
  编号式伪标题、疑似样板行
- 判定分流：`ok` / `sparse` / `flat` / `empty`
- 语料级：跨文件重复行（出现在过半文件中 → 样板行，索引前剥离）
- `--json` 输出便于接流水线

### 解决方案（四层，按投入排序）
1. **审计 + 分流**（已实现）：好的直接用 `md_to_tree`，坏的单独处理，不搞一刀切
2. **轻量规范化**（预处理，不改源文件）：加粗→`#`；无标题则用启发式插标题
   （短行 + 空行包围 + 无句末标点）；剥离样板行
3. **LLM 重排**：让模型只输出**标题结构**（不重写内容），按行号回填，避免内容被改写
4. **放弃标题树，改内容聚类**（兜底最鲁棒）：按 token 窗口分块 → 每块摘要 →
   聚类合成两级树。即 PageIndex 给文件系统做的「虚拟节点」思路下沉到文档内部

### 用户提到的三类内容的处理建议
- **标题**（文档头部报告名/日期）→ 抽成**文档级元数据**，不要当节点
- **页面**（页码标记）→ ⚠️ **是资产不是噪声**，转成 `<!-- page: N -->` 保留，
  正好补上 md 缺失的页码锚点，让引用能回到「第 N 页」
- **附加信息**（附录/术语表/免责声明）→ **单独归类并降权**，标记 `boilerplate: true`，
  检索默认排除（每份都有、措辞雷同，会污染检索）

### PPT 转 md 的特殊处理
**不要试图恢复层级** —— slide 本身就是天然的内容单元，比章节更可靠。
直接把每个 slide 当一个节点（`Slide N`/分隔符切分，slide 首行当标题），
得到「扁平但内聚」的树。深度 1 不一定是坏事：20–30 个内聚节点，
模型看标题就能选。**关键是节点内聚 + 标题有信息量，而不是树有多深。**

## 追加：让大模型直接生成树结构 —— 实测结果（用户提出）

用户提议「把整篇 markdown 丢给大模型让它生成树，不是完美？」

### 朴素做法**灾难性失败**（实测）
把 38 行无标题中文财报 + 行号前缀丢给 `deepseek-flash`，要求输出带标题的树 JSON：
- `max_tokens=4000` → `finish_reason=length`，**4000 全是 reasoning tokens，content 为空字符串**
- 改写提示词、`max_tokens=8000` → **同样 finish=length，8000 reasoning，content 空**

reasoning 轨迹暴露根因：**任务自相矛盾** —— 一边要「生成章节标题」，一边要
「不要新增或改写内容」。无标题文档里章节标题根本不存在，生成必然等于改写。
模型在这个矛盾里打转，把输出预算烧光，一个 token 内容都没产出。

### 关键发现：`reasoning_effort='none'` 可完全关闭推理
deepseek-flash 支持（`thinking={'type':'disabled'}` 等效）。
实测 5 行小输入：`low` → 236 reasoning tokens；`none` → **0 reasoning，27 tokens**。

### 修正后的做法（实测有效）
两处改动：① `reasoning_effort='none'` ② **只要求切分点（行号），不要标题**。
结果：`finish=stop`、128 tokens、返回 **9 个切分点，7 个业务章节全部命中** + 标题 + 附录。
标题由程序从每段首行截取 → 零幻觉。
（注意：第一次测出「命中 2/8」是我的 truth 校验写错了 —— 源文件里章节标题不是独立行，
而是正文首行；模型给的 start_line 其实全对。）

### 为什么 PageIndex 自己不这么干
看 `EXPAND_PROMPT`：一次只给**一个章节**（不是整篇）、给出章节标题与页码范围、
**明确允许返回空**（"If this section is continuous prose... return an empty list.
That is a valid and expected answer."），返回后**校验标题必须在正文里逐字出现**。
→ 刻意避开「给我整篇、生成一棵树」的开放式任务：**收窄 + 给退路 + 结果校验**。

### 方案对比
| 方案 | 输入 | 输出 | 实测 |
|---|---|---|---|
| 朴素：整篇→带标题的树 | 全文 | 树 JSON | ❌ 空返回 |
| 修正：整篇→只要切分点 | 全文 | 行号数组 | ✅ 7/8 章节命中 |
| PageIndex expand | 单章节 | 子标题 | ✅ 且带校验 |
| 正则（现状） | 全文 | 标题 | ⚠️ 无标题文档产出空树 |

### 三条必须的工程约束
1. **关推理**（`reasoning_effort='none'`）或给极大 max_tokens
2. **只让模型出「锚点」，不出「内容」** —— 标题/摘要由程序或后续独立调用生成
3. **锚点必须校验** —— 行号越界检查 + 该行是否真的像标题
4. 分层：正则优先（免费、确定），**只把失败文档送模型**；
   送的时候**只送候选行**（短行 + 空行包围）而非全文，可省 ~80% token

## 追加：Dify 知识库改进方案（用户真实生产问题）

用户场景：公司已有 Dify 知识库，PDF→markdown→向量检索，**财务/表格类查询准确率低**。

### 关键判断
**PageIndex 解决「找对地方」（召回），不解决「算对数字」（精确）。**
财务准确率 = 找对地方 × 取对数字 × 算对结果，三者要分别解。
即使上了 PageIndex，最后仍是让模型从文本里"读"数字 → 依然概率性。
**表格/数字必须走确定性通道。**

### 诊断的四个失败模式
1. 表格被固定长度切分 → 行列关联断裂，回来的是数字孤岛
2. 相似度对数字无效（「2024年每股股息」vs「2023年」嵌入距离≈0）
3. top-k 硬截断 → 排 k+1 静默消失，模型不会告诉你漏了
4. 无确定性通道 → 精确值和算术都没有保障

### 已产出设计文档 `docs/dify-improvement-plan.md`
三层方案：
- **A（1–2 天，必做）**：Dify 原生能力用满 —— 混合检索（全文能精确命中数字串）、
  Rerank、**父子分段**（注意仅 High Quality 索引支持）、按标题层级分块、
  表格整表不切、metadata 注入文件名/报告期/章节路径/页码
- **B（2–4 周，优先）**：双通道 —— 正文走向量，**表格解析入库（DuckDB）+ LLM 生成 SQL +
  代码执行**。直击痛点。Dify 侧用**工作流** + 自定义工具（OpenAPI），
  不要用 Code 节点（沙箱装不了 DuckDB）
- **C（按需）**：Dify **External Knowledge API**，完全替换检索层，上层应用零改动

### Dify External Knowledge API 契约（官方文档，备查）
`POST {endpoint}/retrieval`，`Authorization: Bearer {API_KEY}`
请求：`{knowledge_id, query, retrieval_setting:{top_k, score_threshold}, metadata_condition}`
响应：`{records:[{content, score, title, metadata}]}`

⚠️ 三个坑：
1. **`score_threshold` 是 Dify 传进来的，服务端必须自己过滤**（Dify 不替你过滤）
2. **`score` 必须 0–1，而 PageIndex 没有天然相似度分数** → 要自己造
   （模型置信度 / 按名次衰减 / 多信号融合）
3. **`metadata` 不能是 `null`**，必须 `{}`，否则 Dify 检索管线报错

### 最重要的两条实操建议
1. **先建评测集（50–100 个真实问题 + 精确答案 + 来源），测出基线再改** —— 
   没有评测集所有改动都是盲目调参，这一步 ROI 最高
2. **把「报告期」抽成 metadata**，检索时用 `metadata_condition` 过滤 ——
   财务问答大半错误来自跨期混淆，这一个动作可能消掉一半错误，成本极低

## 追加：实测「跨年份重复文本」对向量检索的破坏程度

用户问「2023 vs 2024 的 VONB/OPAT 在大量重复下，向量相似度有多少区分度」。
做了完整实测（新增 `scripts/05_similarity_probe.py`，用 fastembed 的
BAAI/bge-small-en-v1.5）。

### 环境踩坑
- 本机**无任何 embedding 能力**：DeepSeek 无 `/embeddings` 端点，venv 里
  sentence-transformers / fastembed / numpy / sklearn 全缺
- 装了 `fastembed`（ONNX，比 torch 轻），但**huggingface.co 连不上**（超时）
- 解决：`export HF_ENDPOINT=https://hf-mirror.com`（**必须记住这条**）
- 多语言模型 `paraphrase-multilingual-MiniLM-L12-v2` 下载失败（Xet CAS 401），
  默认英文模型 `BAAI/bge-small-en-v1.5` 可以

### 核心实证 1：两段「定义块」字符级完全相同
FY2023 年报 p13 与 FY2024 年报 p7 的 VONB/OPAT 定义附注：
**700/700 字符，字符级相似度 1.000000，零差异**。
→ 任何 embedding 模型都无法区分，余弦相似度恒等于 1。

### 核心实证 2：正确答案被挤出 top-k
四个 chunk（C1=FY2023定义, C2=FY2024定义, C3=FY2023业绩, C4=FY2024业绩），
问「What were the VONB and OPAT figures in 2024?」：
| 排名 | 相似度 | chunk |
|---|---|---|
| #1 | 0.6334 | C1 FY2023 定义块 |
| #2 | 0.6334 | C2 FY2024 定义块 |
| #3 | 0.5974 | **C4 FY2024 业绩正文（正确答案）** |
| #4 | 0.5956 | C3 FY2023 业绩正文 |

- **榜首与榜二差距 = 0.0000**（完全无法区分）
- **正确答案排第 3**，被两段一模一样的定义文本挤下去
- C4(2024业绩) 0.5974 vs C3(2023业绩) 0.5956 → **差距仅 0.0018，等同噪声**
- 若 top_k=2，拿到的两段都是定义、**不含任何数字** → 模型只能编

### 核心实证 3：全语料规模（10 份 AIA 报告，2,595 个 chunk）
- 相似度 ≥ 0.97 的**跨文档** chunk 对：**1,824 对**
- 涉及 chunk：**1,481 / 2,595 = 57.1%**
- 最相似的 10 对里 **8 对是 1.000000**，全是 1H2024 与 1H2025 的对应页
  （p151/p138/p135/p134/p128/p127/p106/p104，连页码都一样）
- 问「2024 VONB/OPAT」→ **榜首是 FY2023 p59**（错年份！），差距仅 0.0128
- 问「VONB/OPAT definitions」→ 榜首榜二榜三来自 3 个不同文档，
  差距仅 0.0069，且 1/3 槽位被重复文本占用

### 结论
**重复文本不只是"降低准确率"，而是系统性地吃掉 top-k 配额**：
top_k=3 里可能 2 个位置放的是同一段文字，零新增信息。
**只有元数据（doc + period + page）能解决，任何 embedding 模型都做不到。**

### 复用
`scripts/05_similarity_probe.py <目录>` —— 量化语料的跨文档重复率 +
测给定问题的检索区分度。可直接用在他们的 Dify 知识库上做体检。

## 追加：`nav/` 两级导航检索（用户要的增强版）

### 三个关键设计（都是踩坑换来的）
1. **第 1 级读完整目录树，不逐层下钻**。目录数远小于文件数，完整目录树
   一直塞得下 → 两次调用（选目录 + 选文件），与深度无关。
   仅当目录数 > `DIR_TREE_BUDGET`(240) 才退回逐层。
2. **提示词必须强制「至少选 1 个」**。⚠️ 早期写了「都不相关时留空」，
   结果模型**不可预测地**返回空列表、在可回答的问题上直接中止导航
   （同一问题连跑两次一次选中一次不选）。删掉「留空」这个出口后稳定。
   **教训：模型的默认倾向是保守，别给它留空的出口。**
3. **每级都有确定性回退**（年份权重 3 + 中英文词元匹配）。
   逐层下钻中优先回退到**本层文件**而非全语料 —— 回退到全语料语料越大越糟。
   **年份是最强的路由信号**（目录路径通常带年份，跨期混淆是最大错误源）。

### 为什么值得做
默认路径（PyPDF2 读 PDF 文本层）在财报上有两个硬伤（都是之前实测过的）：
1. **表格糊掉** —— 图表页抽成 `175230`（175 和 230 粘一起），标签与数值关联丢失
2. **扫描件直接拒绝** —— 无文本层、无 OCR（`flash_rejection_reason` 会报错）

Azure 的 `prebuilt-layout` 两件都能解：**表格返回真正的 Markdown 表格**，
图片页 **OCR**。而且能补回页码锚点。

### Azure DI REST API 关键事实（备查）
```
POST {endpoint}/documentintelligence/documentModels/{modelId}:analyze
     ?api-version=2024-11-30&outputContentFormat=markdown&stringIndexType=unicodeCodePoint
Header: Ocp-Apim-Subscription-Key: <key>
Header: Content-Type: application/pdf     ← 二进制上传
Body:   raw PDF bytes
→ 202 + Operation-Location + Retry-After
GET {operation-location} 轮询 → {status, analyzeResult}
```
- 模型：`prebuilt-read`（仅文本，最便宜）/ `prebuilt-layout`（表格+标题，**财报用这个**）
  / `prebuilt-document`（加键值对）/ 自定义
- `outputContentFormat=markdown` 官方描述："Markdown representation of the document
  content with section headings, tables, etc."
- 也可用 JSON body 传 `base64Source` 或 `urlSource`
- features 可选：`formulas`（财报有用）、`ocrHighResolution`、`languages`、
  `barcodes`、`keyValuePairs`、`styleFont`

### ★ 页标记注入技巧（本方案的核心价值）
Azure 返回的是一整串 `content`，页边界在 `analyzeResult.pages[].spans[].offset`。
**按 offset 倒序**插入 `<!-- page: N -->`，避免前面的插入导致后面位移。
这就补回了 Markdown 路径本来会丢掉的页码引用（正是之前 `nav/README.md`
里建议的「页码锚点」）。

⚠️ **`stringIndexType` 必须是 `unicodeCodePoint`**（默认已设）——
官方文档明确 "Used by Python 3"。若用默认的 `textElements`（字素簇），
offset 与 Python 字符串下标对不上，页标记会插错位置。
