# Dify 知识库财务问答改进方案

> 历史设计文档（2026-09-23），与 superindex 当前实现无对应关系。

> 场景：现有 Dify 知识库，PDF → Markdown → 向量检索。财务、表格类查询准确率低。
> 目标：在 Dify 框架内，参考 PageIndex 的思路做改进。

---

## 一、问题诊断

当前链路的失败点有四个，而且**它们互相叠加**：

### 1. 表格被切碎
Markdown 表格按固定长度分块时，会被从中间切断。一张 20 行的股息表切成三块后，
「Total dividend 146.00」这一行可能落在某一块，而它的表头（哪一列是 2021）落在另一块。
**行与列的关联断裂**，检索回来的是没有意义的数字孤岛。

### 2. 相似度对数字无效
「2024 年每股股息」和「2023 年每股股息」这两段文本，在嵌入空间里的距离
**几乎等于零** —— 措辞、句式、实体全都一样，只有年份不同。
向量检索在这种情况下的命中基本是抛硬币。

这正是 PageIndex 反复强调的：**相似 ≠ 相关**。在财务领域，语言高度重复，
而微小的差异恰恰携带全部关键信息。

### 3. top-k 是硬截断
如果正确的块排在 k+1，它就**静默消失** —— 不报错，只是答案变差。
财务问题往往需要多个精确值（对比、求和、求增长率），
漏一个就会得出错误结论，而且模型不会告诉你它漏了。

### 4. 没有确定性通道
「2024 年相比 2023 年每股股息增长了多少」这类问题需要：
- **精确值**（不是"相似的文本"）
- **算术运算**（不是语言模型的心算）

向量检索本质上只能提供"看起来相关的文本"，对这两件事都没有保障。

---

## 二、关键认识：PageIndex 解决什么，不解决什么

这一点必须先说清楚，否则方案会跑偏。

**PageIndex 解决的是「找对地方」（召回），不解决「算对数字」（精确）。**

财务问答的准确率其实是三个因子的乘积：

| 环节 | 问题 | 谁来解 |
|---|---|---|
| **找对地方** | 相关段落在哪一章哪一页？ | 结构导航（PageIndex 思路） |
| **取对数字** | 那一格到底是多少？ | **精确查询（结构化通道）** |
| **算对结果** | 增长率是多少？ | **代码执行** |

即使上了 PageIndex，把正确的段落读进来，最后仍然是**让大模型从文本里"读"出数字** ——
这依然是概率性的，不能保证精确。

所以：**表格和数字必须走确定性通道，这是绕不过去的。**

---

## 三、方案 A：最小改动（1–2 天，先做）

不动架构，把 Dify 原生能力用满。这一步是后续所有方案的地基。

### A1. 检索模式改为混合检索

Dify 支持三种模式：向量检索 / 全文检索 / 混合检索。

**从纯向量改为「混合检索（向量 + 全文）」**，理由很直接：
全文检索能**精确命中数字串**。「146.00」在全文索引里是一个可精确匹配的 token，
而向量检索会把它和「135.00」「175.48」混在一起。

对财务场景，全文检索补上的正是向量最弱的那一环。

### A2. 开启 Rerank

混合检索的结果需要重排。Rerank 模型对「哪个块真正回答了问题」的判断
比向量相似度准得多，能把正确答案从 k+1 提到 k 以内。

### A3. 开启父子分段（Parent-Child）

⚠️ 注意：父子分段**只支持 High Quality 索引模式**，Economy 模式不支持。

这个功能正好对应 PageIndex 的「先定位节点、再读整节」：

- **子块**小（单行、短句）→ 精确匹配友好，数字类查询命中率高
- **父块**大（完整章节）→ 上下文完整，喂给模型的信息不缺斤少两
- 检索命中子块，但返回父块内容

### A4. 分块规则：按标题层级切，不要固定长度

你们的 Markdown 有标题（哪怕不规范），**优先按标题边界切**。
固定长度切分是表格断裂的直接原因。

### A5. 表格整表不切

Ingestion 时把 Markdown 表格识别出来，**整张表作为一个独立 chunk**，
并在 metadata 里标记：

```json
{
  "type": "table",
  "doc": "AIA_Annual_Report_2024.md",
  "period": "FY2024",
  "section": "Chairman's Statement > Dividend",
  "table_title": "Dividend per share"
}
```

### A6. chunk metadata 注入结构信息

每个 chunk 带上：**文件名、报告期、章节路径、页码**。
这是引用可追溯的基础，也是后续做元数据过滤的前提。

Dify 的 `metadata_condition` 支持 `is` / `in` / `>` / `<` 等操作符，
有了这些字段，就可以做「只在 FY2024 的报告里搜」这类精确限定 —— 
**这本身就是一个巨大的准确率提升**，因为直接把「跨年份混淆」这个失败模式从根上砍掉了。

### A 阶段的预期

能明显改善召回，但**不解决数字精确性**。适合先做、先测、先建立基线。

## 四、方案 B：双通道（推荐，2–4 周）

**这是直击你痛点的方案。** 架构见对话中的图。

### 核心思想

**表格和正文走不同的通道。** 正文继续走向量，表格走结构化查询。

### Ingestion 分流

```
Markdown
  ├─ 正文/叙述  → Dify 知识库（混合检索 + 父子分段）
  └─ 表格       → 解析成结构化表 → DuckDB / SQLite / Parquet
                   每张表附带元数据：
                   {doc, period, section, table_title, page}
```

表格**不进向量库**（或另建一个专用库）。这是关键：
把表格放进向量库，等于先把结构信息扔掉，再用相似度去猜数字。

### Query 路由与执行

```
用户问题
   ↓
意图路由（LLM 节点）
   ├─ 数值 / 比较 / 计算类  →  结构化通道
   │     1. 按元数据检索相关表的 schema（表名 + 表头 + 元数据）
   │     2. LLM 生成 SQL 查询
   │     3. 执行 → 精确值
   │     4. 结果带来源（文件 · 表 · 行）
   └─ 叙述 / 解释类  →  向量通道（Dify 现有知识库）
   ↓
合并 → 生成答案（带引用）
```

### 为什么这能根治问题

| 原来的问题 | 双通道怎么解 |
|---|---|
| 相似度对数字无效 | 数字不再靠相似度，靠 `WHERE period = 'FY2024'` 精确筛选 |
| 表格被切碎 | 表格整表入库，行列关联完整 |
| 模型心算出错 | 运算交给 SQL / 代码，不由模型心算 |
| 无法追溯 | 每个值都能指回「哪份文件 · 哪张表 · 哪一行」 |

### Dify 侧的实现要点

1. **用「工作流」而不是简单对话应用** —— 需要条件分支和变量聚合
2. **结构化查询服务做成自定义工具（OpenAPI）**，而不是用 Code 节点
   - 原因：Dify 的 Code 节点是受限沙箱，装不了 DuckDB 这类依赖
   - 做成一个 HTTP 服务：`POST /query_table {question, doc_filter}` → 返回精确值 + 来源
   - 在 Dify 里注册成 OpenAPI 工具，工作流里用 Agent 节点或 LLM 节点调用
3. **变量聚合节点**合并两路结果
4. **引用格式**统一成 `{文件} · {表名} · {行}` 或 `{文件} · p{页码} · {章节路径}`

## 五、方案 C：外部知识库 API（最贴近 PageIndex，改动最大）

Dify 提供了一个扩展点，可以**完全替换它的检索层**：
**External Knowledge API**。

### 契约（官方文档）

```
POST {your-endpoint}/retrieval
Content-Type: application/json
Authorization: Bearer {API_KEY}
```

请求体：

```json
{
  "knowledge_id": "your-knowledge-id",
  "query": "What is Dify?",
  "retrieval_setting": { "top_k": 3, "score_threshold": 0.5 },
  "metadata_condition": {
    "logical_operator": "and",
    "conditions": [
      { "name": "period", "comparison_operator": "is", "value": "FY2024" }
    ]
  }
}
```

响应体：

```json
{
  "records": [
    {
      "content": "检索到的文本块，Dify 会把它作为上下文喂给 LLM",
      "score": 0.98,
      "title": "AIA_Annual_Report_2024.md",
      "metadata": { "page": 15, "section": "Chairman's Statement > Dividend" }
    }
  ]
}
```

在 Dify 里配置「外部知识库」指向你的服务地址，之后上层应用**零改动** —— 
还是同一个知识库接口，只是背后换成了你的检索实现。

### ⚠️ 三个必须注意的坑

**坑 1：`score_threshold` 是 Dify 传进来的，你必须自己按它过滤**

Dify 把阈值传给你，但**不替你过滤外部结果**。你要在服务端实现：
`records = [r for r in records if r.score >= score_threshold]`。
忘了做，阈值设置就完全失效。

**坑 2：`score` 必须是 0–1，而 PageIndex 没有天然的相似度分数**

这是这个方案最需要设计的部分。PageIndex 走的是推理路径，不产生余弦相似度。
你需要自己造一个分数，可选做法：

- 让检索模型输出一个 0–1 的置信度
- 按返回名次衰减（1.0 / 0.9 / 0.8 …）—— 粗糙但能配合阈值工作
- 多信号融合：命中节点深度 + 摘要与问题的语义匹配 + 是否命中表格

**坑 3：`metadata` 不能是 `null`**

必须给 `{}`。文档明确写了 `null` 会导致 Dify 检索管线报错。

### 什么时候值得上 C

当方案 A 的分块改进做完之后，**如果召回仍然不理想**（找不到正确段落），
再上 C。如果召回已经够用、问题只在数字精确性，那 B 才是重点，C 是过度投入。

## 六、三者怎么组合

| 方案 | 解决什么 | 投入 | 建议 |
|---|---|---|---|
| **A** | 召回质量、跨年份混淆 | 1–2 天 | **必做**，是地基 |
| **B** | 数字精确性、表格查询 | 2–4 周 | **优先**，直击痛点 |
| **C** | 召回质量（更彻底） | 4–8 周 | 按需，A 不够用时再上 |

**推荐路径：A + B，C 作为后续演进。**

理由：你的痛点是「表格、数字查询准确率低」，这主要是 B 要解决的问题。
A 是低成本的前提条件。C 虽然最接近 PageIndex 的完整思路，
但它优化的是「找对地方」，而你的问题更多在「取对数字」。

## 七、落地路线图

### 阶段 0：建立评测集（最重要，先做）

**没有评测集，所有改动都是盲目调参。**

从真实业务问题里挑 **50–100 个**，每个标注：
- 问题
- 正确答案（精确值）
- 来源（哪份文件、哪张表、哪一行/页）
- 问题类型（单值查找 / 对比 / 计算 / 叙述）

然后测出当前基线的准确率。**之后每一步改动都跑一遍这个集子。**

这一步的投入产出比远高于任何技术改动 —— 它让后续所有决策从猜测变成测量。

### 阶段 1：方案 A（1–2 天）

- 混合检索 + Rerank
- 父子分段（注意需 High Quality 索引）
- 按标题层级分块
- 表格整表不切
- metadata 注入结构信息（文件名 / 报告期 / 章节路径 / 页码）
- **跑评测集，记录提升**

### 阶段 2：方案 B（2–4 周）

- 表格抽取与结构化入库（DuckDB）
- 结构化查询服务（HTTP + OpenAPI）
- Dify 工作流：意图路由 → 双通道 → 合并
- **跑评测集，分类型看提升**（数值类应该提升最明显）

### 阶段 3：方案 C（按需）

- 实现 External Knowledge API 契约
- 背后挂 PageIndex 树检索
- 注意 score 设计、阈值过滤、metadata 非 null
- **跑评测集**

## 八、一个容易忽略的点：报告期是最强的过滤维度

财务问答的一大半错误来自**跨期混淆** —— 问题问 2024，检索回来 2023 的段落。

如果在 ingestion 时把**报告期**抽成 metadata（从文件名、标题、或正文里提取），
那么每次检索都可以带上 `period` 过滤条件：

```json
"metadata_condition": {
  "conditions": [{ "name": "period", "comparison_operator": "is", "value": "FY2024" }]
}
```

**这一个动作可能就消掉了一半的错误**，而且成本极低。
在方案 A 里就该做掉。

## 附：与 PageIndex 思路的对应关系

| PageIndex 的做法 | 本方案的对应 |
|---|---|
| 树索引代替向量索引 | 结构化 metadata + 父子分段 + （可选）外部知识库 API |
| 先定位章节、再读正文 | 父子分段：命中子块 → 返回父块 |
| 用推理而非相似度选分支 | 意图路由 + 元数据过滤 + SQL 精确查询 |
| 表格/数字需要确定性 | **结构化通道：表格入库 + 代码执行** |
| 可追溯引用 | chunk metadata 带文件 / 页码 / 章节路径 / 表名 |
| 查询成本与文档长度解耦 | 元数据过滤先缩小范围，再检索 |
