1Problem Statementsimilarity is not relevance

Vector retrieval returns the passage whose meaning is closest to the question. On financial and regulatory documents, the closest passage is routinely the wrong one — and the reason is structural, not a tuning problem.

An embedding turns text into a list of numbers so that texts meaning similar things land near each other. Ask a question, embed it, return the nearest passages. This works well on prose. It fails on documents that are supposed to be near-identical.

Two consecutive years of a dividend note:

AIA_AR2024.md  p.118   Dividends per share: 175.72 HK cents
AIA_AR2023.md  p.112   Dividends per share: 175.72 HK cents

Change one digit and the embeddings stay almost identical, because almost all of the input is the same. No distance metric can separate two texts whose content is the same. We measured it on a real corpus: 57% of chunks had a near-duplicate in another document, some of them character-for-character identical.

The root cause Similarity is a property of the text. Relevance is a property of the question. When two passages are near-identical, the text cannot tell you which one the question is about — only the structure around it can: which year, which entity, which report.

There is a second failure, and it arrives earlier. PageIndex's tree models one document — the right unit for "where in this report is the figure?", and it answers that well. But a real corpus is not one report. It is thousands of files in a directory tree several levels deep, and the first question a user asks is not where in this report but which report at all.

One document (PageIndex)A corpus (the real deployment)
Unit of addressingPage range inside one treeNeed to pick which document before any page range means anything
Document discoverybrowse_documents returns a flat listA flat list of 1,000 names gives the model no basis for choosing
Directory structureNot modelledThe directory tree is the strongest routing signal available — year, entity, report type
ExtractionPDF text layerMangles tables; refuses scanned PDFs outright
What that leaves us needing A retrieval design in which the answer is produced by decisions that can be printed, logged and configured — rather than by a distance that can only be believed.

2How SuperIndex Solves the Problemnavigate, don't compare

Replace one distance with three decisions. Narrow the corpus before reading anything: which folder, which file, which section. Only then read — and read a single time.

That single change is the whole design. Retrieval becomes a sequence of choices — which folder, which file, which section — instead of a distance you have to trust. Choices can be printed, logged, argued with, and configured by the people who own the documents.

The load-bearing consequence Because nothing is ranked by similarity, there is no embedding model, no vector database and no numpy anywhere in the stack. The only thing that costs money is asking a model to choose between candidates — and that happens a bounded number of times per question, regardless of how deep the folders go.

2.1Build Index

Indexing runs in two stages, and the first one is free.

  1. Structure. Extract text, derive a chapter tree, write the manifest and one tree file per document. No LLM, no API key, no network. On a 144-file / 2,304-node corpus this takes 0.09 seconds.
  2. Summaries. Ask a model for a one-line description of each file and directory, so routing has something to reason over beyond a folder name. This is the only stage that costs money, and it is incremental.

That order matters commercially: you can index an entire corpus, inspect its structure, and decide whether it is worth summarising — before paying for anything.

The index is deliberately split by how often it is read, not by document. The part needed to decide where to look is small and always loaded; the part needed to read a document is large and fetched only for the handful of files that survive routing.

0.09 sstructural index over 144 files / 2,304 nodes — no LLM, no API key
125 KBmanifest for those 144 files, re-read on every query
~2K tokthe entire directory tree — 8,904 characters, one prompt
Why the split is load-bearing The manifest grows with file count, not with document size. A thousand documents is still a few hundred KB of routing index — so routing never touches the bulk of the index, and the expensive half is read only for documents that actually get opened.

Two engines, one tree shape

Text is turned into a chapter tree by whichever engine fits the document. The two have very different cost profiles, and the choice is per document.

Because the flash skeleton needs no LLM, an entire corpus can be parsed and its structure inspected before spending anything — which is what makes the 144-file corpus cheap to work with. The classic path is more accurate when a document has a real table of contents, but note what ships beside it: check_if_toc_extraction_is_complete, check_if_toc_transformation_is_complete, _validate_physical_indices. Those exist because the LLM step is not reliable and has to be verified.

Re-indexing is incremental

Adding one document to a corpus of a thousand should not cost a thousand documents' worth of work. The gate is a size + mtime comparison against the manifest, plus a builder version — so the cost of a re-index is proportional to what actually changed.

The subtlety Size and mtime alone are not enough. When the extraction logic changes, every file's size and mtime stay identical while the tree they produce would be different — so a BUILDER_VERSION constant is part of the gate. Bump it and the whole corpus re-derives; forget to, and an improvement silently never takes effect.

Where the text comes from

The extraction backend matters more than it sounds, because a tree built from mangled text is wrong no matter how good the navigation is. Extraction is pluggable, and the best available backend is chosen in a fixed order, falling through only when the one above produced nothing usable.

Configured means default Set AZURE_DI_ENDPOINT and AZURE_DI_KEY and every entry point picks it up — no flag to remember. With nothing configured you get the text layer, exactly as before. The backend never switches silently: each run prints which one it used and why.
A configured-but-failing backend aborts the run Degrading quietly to the text layer would hide a wrong key or endpoint and change index quality with nobody noticing. Silent degradation is the worst class of bug in a retrieval system, so it is made loud. AZURE_DI_FALLBACK=1 opts into the soft behaviour.

2.2Query

A question is answered by walking three levels in sequence. Each level is an index into the next, and each level is a model decision — there is no similarity ranking anywhere in the path.

Why this stays cheap as the corpus grows The directory tree is far smaller than the file count — 144 files lived in 229 directories, and the whole directory listing is 8,904 characters (≈2K tokens). Directories are what the first level reads, so level 1 can show the whole tree in one call and its cost does not grow with directory depth.

Put together, the path a question takes is a bounded number of model calls plus one streamed answer. Nothing here scales with corpus size except the length of one listing.

Every decision has a deterministic backstop

If the model returns nothing usable at a level, the pipeline does not dead-end and does not fall back to the whole corpus. It scores the candidates at that level with keyword matching and carries on.

Fallbacks resolve at the current level, not globally Falling back to the whole corpus is a blunt instrument that gets worse as the corpus grows. If the model abstains at a level that already has candidate files, use those files — not all 144.

Why level 1 shows the entire tree instead of descending

The first implementation descended one directory level at a time. It was slower and less reliable, for a reason worth recording:

Level-by-level descentWhole tree in one call
Model callsOne per level — grows with depthTwo, regardless of depth
What the model seesOne level at a time; cannot compare across branchesThe whole shape, including which branch is deeper
Failure modeAn early wrong turn is unrecoverableA wrong branch is still visible in context

Descent is still implemented, and is used automatically when the directory count exceeds a budget (240 by default) — but it is the exception, not the default path.

Three decisions, each with a fallback No step in the query path can return nothing. The worst case is a mediocre candidate set, which is a far better failure than a dead end — and the fallback is recorded, so a degraded answer is visible rather than mysterious.

3Software Architecturea layer, not a fork

Five layers, two of which hold real logic. SuperIndex adds a level above the engine and a pluggable boundary underneath it — and modifies nothing in between.

3.1The layered view

3.2A layer, not a fork

The engine lives in superindex/engine/, derived from PageIndex at commit 71714e8 (renamed and trimmed to local mode; see docs/engine/UPSTREAM.md). SuperIndex customises it through explicit extension points rather than ad-hoc edits, so the boundary between engine and layer stays visible.

ExtensionMechanismWhy not edit upstream
Extraction backend
superindex/extractors/backend.py		 Passed in through the engine's page_text_extractor= extension point — a callable returning one string per page, so a drop-in replacement is sufficient. The engine keeps one PDF code path; which backend fills it is decided outside the engine.
Corpus navigator
superindex/nav/		 Sits entirely beside upstream. It builds its own index and never calls into superindex/engine/ for retrieval. The navigator answers a different question (which file?) than upstream does (where in the file?). Keeping them separate means either can be replaced alone.

Both are possible because of the property from §2.1: the indexing engines emit the same tree shape, so nothing downstream depends on how a tree was built. SuperIndex changes where text comes from and how many documents are addressed — not how a tree is shaped or traversed.

3.4Storage and the node model

The tree and the page text are stored separately. The tree is small and can be held in memory; the text is large and fetched on demand. node_id plus a page range is what makes an answer citable.

This split is worth copying SuperIndex's own navigator uses the same shape one level up: a small always-loaded manifest.json for routing, and large per-document trees fetched by key. Storage is plain JSON throughout — readable with cat, and requiring no service to be running.

3.5The loop upstream still provides

Inside a single document, PageIndex offers an agentic loop: the model is given four read-only tools and a tree, and decides for itself what to open. SuperIndex does not use it on the query path — a bounded set of routing calls followed by one streamed answer is cheaper and more predictable — but it remains available, and it is the reason a page number can be cited at all.

Why get_document_structure paginates It splits oversized trees via _split_structure and _split_oversized_node. On the sample annual-report PDFs this is observable: a 452,593-character tree comes back as 9 parts. Intentional, not a defect — but it is the main driver of retrieval cost on that path, because every part is a round trip.

3.6Business knowledge is configuration

Someone inside the business knows that statutory reports live under annual/, that _drafts/ must never be searched, that "太保" and "中国太保" are the same company. That knowledge belongs to the business, so it lives in config/routing_policy.yaml — editable without touching Python, and re-read on every question so there is nothing to restart.

KnobEffectStrictness
directories.excludeRemoves a directory from the candidate setMatches a whole path segment — so draft does not catch drafting-guidelines/
directories.weightsBiases the ranking, and is labelled in the promptMatches a substring or glob; weights accumulate
directories.scopesAdvisory hint rendered into the promptPure suggestion, never filters
periods · aliasesExtra year formats and synonym groups for the fallback matcherExpansion only; never removes candidates
instructionsFree text appended to the selection promptsSoft rules — precedence, tie-breaking
Empty policy = built-in behaviour Delete the file and routing behaves exactly as if the feature did not exist. Every rule is an addition, never a switch — which is the only reason it is safe to hand this file to a business user. A malformed file logs to results/logs/errors.jsonl and falls back to the defaults rather than failing the query.

3.7Every answer is auditable

Because the answer came from decisions, the decisions can be printed. Internal identifiers never reach the model or the user — paths are translated to readable names at the boundary, so what you audit is what was actually asked.

Stage timings alone cannot tell "the model was called five times" apart from "one call silently retried twice" — a retry happens inside a stage total, so afterwards both look identical. Every query record therefore carries a per-call breakdown: which stage, how long, how many attempts, and whether it retried.

模型调用 5 次 · 3.1s · 最慢 0.8s route.dirs
模型调用 3 次 · 4.2s · 重试 2 次 · 最慢 4.0s route.sections 友邦保险 / AIA_AR2024.md

Read llm_n_retried first: anything non-zero means part of that query's latency went into recovering rather than working. This is not decoration — the instrumentation immediately surfaced a four-second stall on the first question after a server restart, which turned out to be a lazily-imported library fetching a price table over a slow network. That is now paid at startup instead.

3.8Dependency footprint

Grouped by purpose. Three entries are optional extras rather than hard requirements.

Notably missing Any vector store, any embedding model, any numerical library. There is no faiss, no numpy, no similarity index to keep in sync with the documents. Retrieval is a chat model reasoning over an explicit tree — which is precisely what makes an answer traceable to a page number instead of to a cosine score.

520 assertions across seven files, all offline — no network, no credentials, no test framework. Run any file directly and it prints its own pass/fail count.

Two properties of the suite are deliberate. It runs entirely offline, so it can be run on a laptop with no keys and no corpus; and it has zero dependencies — each file is a plain script with its own check() counter, so there is no framework version to drift.

In this repository the same files also run under pytest together with the rest of the suite: uv run pytest tests -q (tests/conftest.py makes a failed check() fail the pytest run); any single file still runs on its own, e.g. uv run python tests/test_policy.py.

4.1Measured performance

Indexing figures are from a 144-file / 229-directory / 2,304-node corpus. Question timings are from 21 recorded queries.

Stage of a questionMeanMaxShare
Answer generation17.9 s93.3 s77%
Routing — pick directories, then files4.2 s12.7 s18%
Section selection — one call per candidate file1.2 s2.8 s5%
End to end23.3 s114.0 s—

The dominant cost is neither retrieval nor context size. The slowest query on record spent 93 seconds answering from a 3 KB context — that is the model thinking. Section selection was the one stage that was purely wasteful: the per-file calls are independent, so they now run concurrently (four files × 0.25 s measured at 0.26 s, not 1.0 s).

Where the lever actually is Answer generation is 77% of the wall clock, so reducing the number of sources and the context length is the only change with real leverage. Local I/O is not a bottleneck: reading and parsing tree.json takes 0.8 ms and pages.json 1.8 ms.

4.2What the tests do not cover

Worth being explicit about, because these are the questions a new owner hits.

LimitDetail
Validated on synthetic corpora16-file and 144-file corpora with a known structure. The scale numbers above are real; routing accuracy on a genuinely messy production corpus is not yet measured.
Locating is not computingThe navigator finds the right section. If the answer needs arithmetic across sections, the model still does it by reading text. Numbers ultimately need a structured path.
Chapter summaries need a modelA one-time cost per corpus. Without them, section selection degrades to token matching.
Directory quality sets the ceilingThousands of files flattened into one folder degrade the first level to listing thousands of names. That is a corpus-organisation problem, not a navigator one.
Fallbacks match tokens, not synonyms"Life insurance" will not match a folder named 人身险. The aliases block fixes the cases you can name; an embedding pre-filter would generalise — at the cost of reintroducing the similarity problem the design exists to avoid.
Navigation costs round tripsSeveral model calls before the answer even starts. This is not a design for sub-second latency budgets.
The honest summary SuperIndex makes the which file, which section problem cheap and traceable at corpus scale, and it is well covered by tests on that path. It does not make numeric answers exact, and it has not been run against a genuinely messy production corpus. Both are known and recorded rather than papered over.
